# 문항 작성·검증·임포트

## 작성 원칙

문항은 AI 개념 이해와 실무 판단을 평가합니다. 제품별 API 암기, 답이 모호한 주장, 시대에 따라 달라지는 제품 수치, 동등한 선택지 중 하나를 임의로 정답 처리하는 문제는 피합니다. 상황·조건·질문을 분명하게 쓰고 단일 정답을 구성합니다. 정답 해설은 이유를 설명하고 모든 선택지에 구체적인 설명을 붙입니다.

초기 은행은 8개 영역마다 초급 3·중급 3·고급 2, 총 64문항입니다. 추가 문항은 독립 JSON 파일로 둘 수 있으며 UI 수정이 필요하지 않습니다. 각 파일과 전체 은행에서 문항 ID는 고유해야 합니다.

## 필드와 허용값

| 필드                 | 요구사항                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| `id`                 | 120자 이하 고유 문자열. 영문·숫자로 시작하고 이후 영문·숫자·점·밑줄·하이픈 허용. 예: `fundamentals-009`  |
| `stage`              | 현재 출제기는 `1`만 지원                                                                                 |
| `type`               | `"single_choice"`                                                                                        |
| `category`           | 아래 표의 영역 ID                                                                                        |
| `difficulty`         | `"beginner"`, `"intermediate"`, `"advanced"`                                                             |
| `stem`               | 문제 본문                                                                                                |
| `options`            | `{ "id": string, "text": string }` 배열. 최소 두 개, 문항 내 ID 중복 금지. ID 문자 규칙은 문항 ID와 동일 |
| `correctOptionId`    | `options`에 존재하는 선택지 ID                                                                           |
| `explanation`        | 비어 있지 않은 정답·개념 해설                                                                            |
| `optionExplanations` | 정답을 포함한 모든 선택지 ID의 해설 map                                                                  |
| `tags`               | 하나 이상의 비어 있지 않은 학습 키워드                                                                   |
| `provenance`         | `"original"`, `"licensed"`, `"user_provided"`                                                            |
| `version`            | 1 이상의 정수. 의미·정답·해설을 수정하면 증가                                                            |
| `status`             | `"published"` 또는 `"review"`                                                                            |

ID로 `__proto__`, `constructor`, `prototype`은 사용할 수 없습니다. 태그와 선택지 해설 key는 중복되거나 알 수 없는 선택지를 참조할 수 없습니다. 스키마에 없는 필드도 거부됩니다.

| 영역 ID        | 주제                                        |
| -------------- | ------------------------------------------- |
| `fundamentals` | AI·ML·DL, 학습과 추론, 지도·비지도학습      |
| `generative`   | 생성형 AI·LLM, 토큰·문맥, 특징과 한계       |
| `prompting`    | 지시·맥락·예시·출력 형식·반복 개선          |
| `verification` | 환각·근거·불확실성·출력 검증                |
| `responsible`  | 편향·공정성·투명성·책임·인간의 감독         |
| `security`     | 개인정보·민감정보·접근 통제·프롬프트 인젝션 |
| `productivity` | 문서·요약·분석·자동화·사람과 AI의 협업      |
| `systems`      | RAG·도구 호출·Agent·워크플로                |

## JSON 예시

다음은 형식 설명용 추가 문항입니다. 기존 은행에 동일한 ID가 있으면 새 ID를 정하세요. 파일 최상위는 문항 배열입니다.

```json
[
  {
    "id": "authoring-example-001",
    "stage": 1,
    "type": "single_choice",
    "category": "verification",
    "difficulty": "beginner",
    "stem": "AI가 작성한 업무 보고서에 구체적인 통계와 출처 링크가 포함되어 있다. 공유 전에 가장 적절한 행동은 무엇인가?",
    "options": [
      {
        "id": "a",
        "text": "문장이 자연스러우므로 통계도 정확하다고 판단한다."
      },
      {
        "id": "b",
        "text": "원출처를 열어 수치와 조사 조건이 보고서의 주장과 일치하는지 확인한다."
      },
      {
        "id": "c",
        "text": "같은 AI에 한 번 더 물어 같은 답이 나오면 확인을 끝낸다."
      },
      { "id": "d", "text": "링크가 있으므로 검증 없이 보고서에 인용한다." }
    ],
    "correctOptionId": "b",
    "explanation": "생성된 출처나 수치도 오류일 수 있으므로 원출처의 존재, 값, 시점과 조사 조건을 직접 확인해야 한다.",
    "optionExplanations": {
      "a": "유창한 표현은 사실 정확성을 보증하지 않는다.",
      "b": "원출처와 주장 사이의 일치를 확인하면 잘못된 수치와 맥락의 오용을 줄일 수 있다.",
      "c": "같은 모델은 일관되게 잘못 답할 수 있어 반복 응답만으로는 독립 검증이 되지 않는다.",
      "d": "생성된 링크가 존재하지 않거나 다른 내용을 가리킬 수 있다."
    },
    "tags": ["출처 확인", "통계 검증"],
    "provenance": "original",
    "version": 1,
    "status": "review"
  }
]
```

검토를 마친 뒤 `status`를 `published`로 변경해야 출제됩니다. 형식 검증 통과는 내용의 정확성·저작권 허가·교육적 품질 검토를 대신하지 않습니다.

## 임포트 형식

```bash
npm run questions:import -- /absolute/path/my-bank.json
npm run questions:validate
npm run test
npm run build
```

- **JSON:** 위 예시와 같은 문항 배열.
- **JSONL:** 각 줄에 한 문항 JSON 객체. 객체 내부의 줄바꿈은 JSON 문자열에서 이스케이프합니다.
- **Markdown:** 하나 이상의 `json` 코드 블록에 각각 문항 배열을 작성합니다. 설명 문장은 데이터로 읽지 않습니다.

임포트는 입력을 파싱하고 스키마·문항/선택지 ID·정답 참조·모든 해설·분류·출처 유형·버전을 검증합니다. 검증을 통과하면 안전한 파일 이름의 JSON을 `src/data/questions/`에 생성합니다. 같은 목적 파일 이름이나 기존 문항 ID가 있으면 덮어쓰지 않고 실패합니다. 입력 파일의 이름은 기존 은행과 구별되는 이름을 사용하세요.

직접 JSON 파일을 추가할 수도 있습니다. 커밋 전 `npm run questions:validate`로 모든 JSON을 합친 은행을 검증합니다. 지원하지 않는 필드나 유형은 현재 스키마에 맞추거나 별도 개발 작업으로 모델을 먼저 확장합니다. 검증기를 통과시키려고 기존 정답이나 의미를 임의로 바꾸지 않습니다.

## 검토와 출처 관리

1. 한 문항에 하나의 명확한 정답이 있는지 확인합니다.
2. 정답과 모든 오답에 이유가 있고 본문 조건과 모순되지 않는지 확인합니다.
3. 영역·난이도·태그, 중복 주제와 정답 위치의 쏠림을 검토합니다.
4. 불확실한 내용은 신뢰할 수 있는 자료로 확인하고 해결되지 않으면 `review`로 유지합니다.
5. `original`은 독창적으로 작성한 문항, `licensed`는 공개 배포 허가를 확인한 자료, `user_provided`는 사용자 제공 자료입니다. 사용자 제공 여부만으로 공개 저장소 재배포 권한이 생기지 않습니다.
6. 외부 자료는 저작권자·허가 범위·원출처·확인일을 검토 기록에 남깁니다. 개인정보·유료 시험 원문·접근 제한 자료는 허가 없이 포함하지 않습니다.

초기 문제은행에는 참고 서비스의 원문 문제가 포함되지 않습니다. 접근 시도와 미확인 사항은 [벤치마크 기록](BENCHMARK_NOTES.md)을 참조하세요.

## 버전과 과거 응시

기존 문항의 의미·정답·해설을 수정할 때에는 같은 ID를 유지하고 `version`을 증가시킵니다. 완전히 다른 문항은 새 ID로 추가합니다. 은행에 같은 ID의 여러 버전을 나란히 두지 않습니다. 문제가 발견되어 출제를 중단할 경우 `status: "review"`로 변경할 수 있습니다.

각 응시는 생성 당시의 문제·선택지·배열·버전을 보관하므로 이후 은행 수정으로 과거 결과를 다시 채점하지 않습니다. 이미 제출된 결과를 UI에서 수정하지 않습니다. 잘못된 과거 학습 내용에 대한 정정 공지가 필요하면 별도의 안내로 제공합니다.

브라우저의 학습 기록 JSON은 문항 은행 추가용 파일이 아닙니다. 개인 기록 백업은 학습 기록 화면에서 내보내고 가져오며 현재 기록 전체를 검증 후 교체합니다.
